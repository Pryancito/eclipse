# Eclipse OS labwc desktop

[Español](README-desktop.md) · **English**

Eclipse OS ships out of the box with a Wayland desktop session based on
**labwc** (wlroots; software pixman renderer, or GLES2/zink with a GPU, see
[README-drm.md](README-drm.md)), with **four interchangeable looks** on top of
exactly the same native pieces: `tecno` (the one the image ships with),
Eclipse's original violet look, KDE Plasma's and Windows 11's. The wallpaper is
always **lunarbg**, the panel is always **lunarbar** and the launcher is always
**lunarrun**; what changes is the palette and the layout.

## The looks

They are picked with `eclipse-look` and stored in `/etc/eclipse/look` (`look=`
on the cmdline wins if present). `eclipse-init` applies it at boot, just as it
does with the language and the time zone.

```sh
eclipse-look            # prints the current one
eclipse-look tecno      # "Orbital HUD" instrument panel (default)
eclipse-look eclipse    # the original violet one
eclipse-look kde        # KDE Breeze Dark
eclipse-look win11      # Windows 11
```

| | `tecno` (default) | `eclipse` | `kde` | `win11` |
|---|---|---|---|---|
| Window theme | `Tecno-Dark` (#0a1423, cyan accent #38e1ff, gold #f2c14e when pressed) | `Eclipse-Dark` (violet) | `Breeze-Dark` (#31363b, accent #3daee9) | `Win11-Dark` (#202020, accent #0078d4) |
| Panel | two 34 px bars, square plates with a fillet; on top the desktops 01–04 and the focused window centred, with segmented `CPU`/`MEM`, `NET` and `TEMP` in gold; gold corner brackets on menus | two 34 px bars (info on top, tasks at the bottom) | one 44 px bottom bar, Plasma-style | one 48 px bottom bar, **centred buttons**, translucent |
| Clock | at the bottom, big and bold (10x20); date on top | one line at the bottom, date on top | two lines, time over date | two lines, time over date |
| Terminal | tecno palette (gold as yellow) | violet palette | Breeze palette (Konsole) | Campbell palette (Windows Terminal) |
| Wallpaper | golden eclipse on black with a greenish halo, thin rings and the caption `ECLIPSE · SYSTEM · KERNEL · ZCORE` | animated cosmos with stars, grid and a text ring | animated cosmos | animated cosmos |
| Files and browser | straight lunarfile, upper-case columns and gold folders; SilverSurfer with the same palette | violet palette | Breeze palette | Windows 11 palette |
| Launcher | in the top third, straight, with gold corner brackets | in the top third | in the top third | Start menu above the bar |

`tecno` is the "Orbital HUD" look from the mock-up Moebius picked (see
[img/tecno-orbital-hud.png](img/tecno-orbital-hud.png)): space black,
instrumentation cyan `#38e1ff`, fillet `#1d3550` and the gold `#f2c14e` of
lunarbg's crescent to mark what has focus.

Changing the look rewrites the theme's `<name>` in `rc.xml` (and the title font:
`DejaVu Sans Mono` in `tecno`, `DejaVu Sans` in the rest), copies the matching
foot palette and restarts the panel and the wallpaper (init relaunches them at
once; both read `/etc/eclipse/look` at start-up); `labwc --reconfigure` reloads
the theme without closing the session.

**Shadows**: the `themerc` files ask for a shadow under windows
(`window.active.shadow.size`/`.color`), which labwc really draws since 0.8. An
older version ignores keys it does not know, so nothing breaks where there is no
support. This is a real compositor shadow; what there is not is blur.

**Translucency**: in `win11` the bar is drawn on an 85 % ARGB buffer and the
launcher menu at 92 %, so the wallpaper shows through. It is **flat**
translucency: Windows' acrylic and Mica blur what is behind the surface and
labwc cannot blur, so there is no frosted effect. No Microsoft font, icon or
wallpaper is distributed: everything is drawn with our own colours.

## What CANNOT be brought over from KDE

Plasma cannot run here, and it is worth knowing why before trying:
`plasmashell`, `kded`, `krunner` and the polkit-kde agent are **D-Bus** services
from top to bottom. That is no longer the obstacle — there is now a real session
bus listening on `DBUS_SESSION_BUS_ADDRESS`, see [README-dbus.md](README-dbus.md)
— but there is still no Qt or KF6 in the image, nor polkit, nor logind (seatd is
used). What is recreated is the experience: theme, shortcuts, panel and
launcher, with Eclipse's native pieces.

The Qt variables (`QT_QPA_PLATFORM=wayland;xcb`, `QT_AUTO_SCREEN_SCALE_FACTOR`,
and `QT_QUICK_BACKEND=software` in the pixman session) are set, for the day a
Qt app is installed. `QT_QPA_PLATFORMTHEME=kde` and `XDG_CURRENT_DESKTOP=KDE`,
which every "KDE on labwc" recipe recommends, are deliberately **not** set: the
first needs the plasma-integration plugin and the second makes the portals and
GTK look for a KDE session that does not exist. `XDG_CURRENT_DESKTOP` says what
this session really is, `labwc:wlroots`.

All the configuration is generated by `xtask` when building the rootfs
(`xtask/src/linux/desktop.rs`), so it is there from the first boot with no
manual steps.

## Components

| Piece | Generated file | What it does |
|---|---|---|
| **lunarbg** | `/bin/lunarbg` | Eclipse OS's **animated** wallpaper client (`tools/lunarbg`, static Rust). It recreates the wallpaper of eclipse-old's original smithay compositor: a central golden crescent, a "ECLIPSE-SYSTEM-KERNEL…" text ring orbiting, three tech arcs spinning at different speeds, pulsing rings and technical ticks, over a cosmic base with stars and a 48 px grid. It draws procedurally at native resolution through wlr-layer-shell + wl_shm (no images, no gdk-pixbuf), rendering with *scanline spans* (~2 ms/frame at 1080p) and only redrawing/damaging the logo region each frame. ## Runtime packages

The kernel does not include the Wayland binaries; they come from the Ubuntu
26.10 packages the build installs into the desktop variant. They are all
optional — the session degrades gracefully if one is missing:

```sh
apt-get install labwc seatd foot wayland-protocols fonts-dejavu adwaita-icon-theme
apt-get install libsdl2-2.0-0 libsdl3-0 libsdl1.2debian libsdl2-image-2.0-0 libsdl2-ttf-2.0-0 libsdl2-mixer-2.0-0 libsdl2-net-2.0-0 libpng16-16t64 libfluidsynth3 libdecor-0-0   # SDL runtime
```

With `cargo xtask image` these packages are already installed on their own (see
`DESKTOP_UBUNTU` in `xtask/src/linux/apt_rootfs.rs`; with `ECLIPSE_PKG=apk`,
`DEFAULT_PACKAGES` in `xtask/src/linux/xorg.rs`): `labwc` pulls in its runtime
closure (wlroots, wayland libs, libinput, pixman, libxkbcommon), `seatd` provides
`libseat.so` and the `seatd` daemon, and `foot` is the terminal.

- `labwc` — the compositor.
- `seatd` — the seat manager; it runs as a **daemon** (an init service, socket
  `/run/seatd.sock`, which `labwc.service` waits on). The wrapper sets
  `LIBSEAT_BACKEND=seatd` (with `:=`, so it can be overridden).
- `lunarbg` and `lunarbar` — wallpaper and panel, included in the rootfs (they
  are not external packages); neither `swaybg` nor `waybar` is needed.
- `foot` — Wayland terminal.
- `fonts-dejavu` — the typeface used by the theme, panel and menus.
- `adwaita-icon-theme` — cursor and icon theme (without it the pointer is not
  visible with a software cursor).

## Xwayland (X11 applications)

labwc can run **legacy X11** applications inside the Wayland session through
**Xwayland**, a rootless X server. Eclipse starts it *with the compositor*, not
on demand: the `rc.xml` the build generates sets
`<core><xwaylandPersistence>yes</xwaylandPersistence></core>` (labwc >= 0.7.3).
Lazy start was ruled out because its failure was not loud — labwc listens on the
socket and **parks** the client waiting for a server that never finished
starting, so an X11 app hung forever instead of failing. It is enabled out of
the box:

- The `Xwayland` binary is installed with the rest of the stack (the `xwayland`
  package in `DESKTOP_UBUNTU`, `xtask/src/linux/apt_rootfs.rs`) and ships both
  to the installed system and to the live/QEMU initramfs (`usr/bin` is in
  `LIVE_TREES`). The build checks for it and warns **loudly** if it is missing.
- The packaged labwc has the support compiled in; with `xwaylandPersistence` the
  server is already up when the session starts, and labwc exports the real
  display number to its children (which is why a terminal in the session
  inherits `DISPLAY` without anyone setting it by hand).
- `DISPLAY=:0` is set in the session environment (`CHILD_ENV` in
  `tools/eclipse-init/src/main.rs`, mirrored in labwc's `environment`), so an X11
  app launched by hand from a `foot` terminal finds the server. With a single
  compositor and no other X server, that display is always `:0`.

Native Wayland clients (foot, lunarbg, lunarbar) ignore `DISPLAY`, and the
GTK/Qt toolkits still prefer Wayland because `WAYLAND_DISPLAY` is present — so
setting `DISPLAY` does not change their behaviour; it only gives X11-only apps a
server to connect to.

Checking that it works from a terminal in the session:

```sh
echo $DISPLAY          # -> :0
glxgears               # GL gears (via Xwayland + nouveau hardware GL)
xterm                  # a classic X11 terminal inside the Wayland desktop
```

If an X11 app fails with "can't open display" even with `DISPLAY=:0`, look in
the build output for the `Xorg stack: Xwayland present …` line: if it says it is
missing, the build could not download the `xwayland` package (most commonly, no
network while building the image) and you need to rebuild with network access or
run `apt-get install xwayland` once.

## SDL (SDL 1.2 / SDL2 / SDL3)

The session ships the **SDL** runtime (`libsdl2-2.0-0`, `libsdl3-0`,
`libsdl1.2debian`, `libsdl2-image`, `-ttf`, `-mixer`, `-net`, `libpng16`,
`libfluidsynth3`, `libdecor-0-0`; see `DESKTOP_UBUNTU` in
`xtask/src/linux/apt_rootfs.rs`) and an **environment policy** that picks SDL's
video backend and *render driver* to match the compositor's renderer. Without
it, SDL2 always took X11 (it picks X11 as soon as `DISPLAY` is set, and here it
is: `:0`), that is, everything went through Xwayland, and Mesa decided the
renderer blindly.

The policy is asserted in the same four places as the wlroots renderer policy,
so that an SDL app launched from a shell and one launched by init render through
the same stack: the `/usr/local/bin/labwc` wrapper, `/etc/profile`,
`~/.config/labwc/environment` (only the static half) and `eclipse-init`
(`push_sdl_render_env`). An `xtask` test
(`sdl_policy_is_consistent_across_wrapper_profile_and_environment`) checks that
the generated copies do not drift apart.

| Session | `WLR_RENDERER` | `SDL_RENDER_DRIVER` | `SDL_FRAMEBUFFER_ACCELERATION` | What SDL does |
|---|---|---|---|---|
| pixman (default without a GPU) | `pixman` | `software` | `0` | Rasterises on the CPU. **SDL3** presents through `wl_shm`, without touching GL (the same path as foot/lunarbg). **SDL2** has no shm framebuffer on Wayland and presents through EGL, which `LIBGL_ALWAYS_SOFTWARE=1` leaves on llvmpipe. |
| gles2 (`nvidia.wlr_gles2`, or `renderer=gl-sw`/`GL=1` in QEMU) | `gles2` | `opengles2` | `opengles2` | GLES2 renderer on the same GL stack as the compositor: zink+NVK on hardware, llvmpipe in software. |
| vulkan (`nvidia.wlr_vulkan`) | `vulkan` | `opengles2` | `opengles2` | Same as gles2: SDL2 has no Vulkan renderer, and GLES2 ends up on zink+NVK. The compositor (not its clients) uses wlroots' native Vulkan renderer on NVK; see "The native Vulkan renderer" below. |

Independent of the renderer, in every session:

- `SDL_VIDEODRIVER=wayland,x11` (SDL2) and `SDL_VIDEO_DRIVER=wayland,x11`
  (SDL3): native Wayland first, X11 as fallback. The list also serves the
  `desktop=xorg` session (without `WAYLAND_DISPLAY`, SDL falls back to X11 on
  its own). The comma syntax needs SDL >= 2.24 (Ubuntu 26.10 ships 2.30+).
- `SDL_AUDIODRIVER=alsa` / `SDL_AUDIO_DRIVER=alsa`: SDL uses ALSA, and
  `/etc/asound.conf` routes it through PulseAudio so that several clients share
  the PCM ([README-audio.md](README-audio.md)). `PULSE_SERVER` points to
  `unix:/run/pulse/native` for those that speak libpulse.
- Decorations: labwc offers server-side decoration through `xdg-decoration`,
  which SDL prefers; `libdecor` stays as the client-side fallback.

Every variable is set with `:=` in the wrapper, so an override from whoever
launches wins (e.g. `SDL_RENDER_DRIVER=opengles2 my-game` to force the GL path
for one client in the pixman session).

**Checking that it works** from a terminal in the session (or from the desktop
menu, entries "SDL2 test (renderer)" and "SDL3 test (wl_shm)"):

```sh
eclipse-sdl-probe                    # SDL2 + SDL_Renderer: expect 'video driver in use: wayland'
eclipse-sdl-probe --sdl3 --surface   #   and "renderer 'software'" on pixman / 'opengles2' on gles2
```

`eclipse-sdl-probe` (`tools/eclipse-sdl-probe`) opens the installed libSDL with
`dlopen`, prints the version, the compiled-in backends, the backend and renderer
in use, and measures the fps of a simple animation; it exits with
`SDLPROBE: FAIL ...` and code 1 if something fails. A
`video driver in use: x11` with `WAYLAND_DISPLAY` present means something
overrode `SDL_VIDEODRIVER`.

## The native Vulkan renderer (`nvidia.wlr_vulkan`)

The default GPU session is **GLES2 on zink+NVK**: the compositor asks Mesa for
GL, Mesa translates it to Vulkan with zink and NVK runs it on the card. With
`nvidia.wlr_vulkan` the compositor skips zink and uses **wlroots' native Vulkan
renderer**, which talks Vulkan directly to NVK. GL clients stay on zink+NVK in
both cases.

### What wlroots really requires

`vulkan_find_phdev` and `vulkan_device_create` (`render/vulkan/`) ask for four
things, and none of them is a semaphore:

1. A Vulkan 1.1 instance and a physical device with `apiVersion` >= 1.1.
2. A physical device with **`VK_EXT_physical_device_drm`** whose
   `primaryMajor:primaryMinor` **or** `renderMajor:renderMinor` pair **equals
   the `st_rdev` of the DRM fd wlroots opened** — that is, `/dev/dri/card0`'s,
   because that is what `WLR_DRM_DEVICES` says. It is the only requirement the
   GLES2 path does not have, and the one that produces the only error line
   wlroots prints when something in the enumeration fails: `Could not match drm
   and vulkan device`.
3. Five device extensions: `VK_KHR_external_memory_fd`,
   `VK_KHR_image_format_list`, `VK_EXT_external_memory_dma_buf`,
   `VK_EXT_queue_family_foreign` and `VK_EXT_image_drm_format_modifier`.
4. A queue with `VK_QUEUE_GRAPHICS_BIT`.

**The blocker that shelved this hatch no longer exists.** It was shelved because
`vkCreateSemaphore` returned `ERROR_INVALID_EXTERNAL_HANDLE`: wlroots asked for
an **external, exportable** semaphore (`VK_KHR_external_semaphore_fd`, for
interoperability with implicit synchronisation) that NVK did not export over our
syncobj uAPI. wlroots' Vulkan renderer **no longer creates a single semaphore**:
it waits on a plain `VkFence` with `vkWaitForFences`. So that reason expired,
and on top of that this tree's syncobj uAPI has grown since then
(`DRM_CAP_SYNCOBJ` / `DRM_CAP_SYNCOBJ_TIMELINE`, `SYNCOBJ_HANDLE_TO_FD` /
`FD_TO_HANDLE` with `EXPORT_SYNC_FILE` / `IMPORT_SYNC_FILE`, `SYNCOBJ_EVENTFD`).
The other two consequences seen back then are also covered: `MAX_CHANNELS` went
from 16 to 64 and `MAX_CTX` from 8 to 32, which is what turned an enumeration
burst into `CHANNEL_ALLOC -> EBUSY`.

### The ladder, and why trying the hatch is now free

wlroots **does not fall back from one renderer to another by itself**: if the
one you ask for does not start, it exits with `unable to create renderer`. The
whole ladder is set up by the `/usr/local/bin/labwc` wrapper, two attempts per
rung:

```
vulkan  ->  gles2 (zink+NVK)  ->  pixman (CPU)
```

The middle rung is what makes the hatch cheap: before, asking for
`nvidia.wlr_vulkan` and having wlroots reject it cost the **entire GPU session**
and left the desktop painted by the CPU. `/run/labwc-renderer-fallback` — which
is how `eclipse-firefox` learns that this session has no GPU path — is written
**only** if pixman is reached.

### The preflight: `/tmp/labwc-vulkan-preflight.log`

Only in this session, and **before** the first attempt, the wrapper records the
inputs to requirements 2 and 3, because wlroots sums them all up in a single
line:

- the ICD the loader is pinned to (`VK_DRIVER_FILES`);
- the `major:minor` of `/dev/dri/card0` and `/dev/dri/renderD128`;
- what `vulkaninfo` says about `primaryMajor/Minor`, `renderMajor/Minor`, the
  device name and the five extensions.

Read it by comparing by eye: if the pair NVK publishes for the card is **not**
`card0`'s `major:minor`, the failure is the matching (requirement 2) and not the
driver. If an extension is missing, it is requirement 3.

Why the loader is pinned to the NVK ICD in this session and **not** in the
default GLES2 one: `mesa-vulkan-drivers` also installs **lavapipe**, the CPU
Vulkan driver, as the floor for Xwayland's glamor. lavapipe has no DRM device, so
it **can never** be requirement 2's match — the Vulkan session cannot sneak off
to the CPU. What an unpinned loader costs is the diagnosis, because lavapipe
shows up in the list looking like a device. It is the same measure
`eclipse-firefox` already takes, for the same reason. The GLES2 session is the
one that works today on Moebius's hardware and its environment is left **byte
for byte** as it was.

## Games (freedoom, supertux2)

**Freedoom comes installed.** Both IWADs (`freedoom1.wad`, `freedoom2.wad`) and
the `chocolate-doom` engine are in the default package set (`freedoom` and
`chocolate-doom` in `xtask/src/linux/apt_rootfs.rs`), because a freshly
installed Eclipse has no mirror at hand right when you feel like seeing whether
the desktop can run a game.

It is launched from the desktop menu ("Freedoom (Phase 1)" / "(Phase 2)"), from
the panel's application menu, or by hand:

```sh
eclipse-freedoom          # Phase 2 (default)
eclipse-freedoom 1        # Phase 1
eclipse-freedoom /path/doom2.wad   # any other IWAD
```

`eclipse-freedoom` (`xtask/src/linux/desktop.rs`) takes care of three things:

- **It always passes `-iwad`.** With several IWADs and without that option,
  gzdoom opens a GTK dialog asking which one to play; it is the first thing the
  user would see.
- **It picks the renderer.** gzdoom needs OpenGL 3.3+ or Vulkan. In the pixman
  session there is no GL driver, so the wrapper forces `LIBGL_ALWAYS_SOFTWARE=1`
  (llvmpipe: it works, but it is slow); in the `nvidia.wlr_gles2` /
  `nvidia.wlr_vulkan` sessions (`WLR_RENDERER` = `gles2`/`vulkan`) it leaves the
  environment alone, so that it uses zink+NVK.
- **It leaves a trail.** Everything goes to `/tmp/freedoom.log`, because a game
  launched from the panel writes to a terminal nobody is looking at.

The wrapper prefers a software engine (`chocolate-doom`, which comes installed,
`crispy-doom` or `prboom-plus`) over gzdoom: on this stack, whose best GL without
a GPU is llvmpipe, that is the one that runs at full speed.

```sh
apt-get install supertux          # binary: supertux2
```

Both games failed on real hardware for different reasons, and both are fixed:

- **supertux2** aborted with `Assertion 'r == 0 || r == 95' failed at
  ../src/pulsecore/mutex-posix.c:57, function pa_mutex_new()`. SuperTux (and
  gzdoom) use OpenAL; openal-soft tries pipewire and pulse first, and loading
  libpulse runs `pa_mutex_new()`, which calls
  `pthread_mutexattr_setprotocol(PTHREAD_PRIO_INHERIT)`. musl probes the kernel
  with `FUTEX_LOCK_PI` and returns the kernel's errno **as is** (there is no
  translation: `if (r) return r;` in `pthread_mutexattr_setprotocol.c`), and
  PulseAudio only accepts 0 or `ENOTSUP`. The kernel now implements
  `FUTEX_LOCK_PI`/`FUTEX_LOCK_PI2`/`FUTEX_TRYLOCK_PI`/`FUTEX_UNLOCK_PI`
  (`linux-syscall/src/misc.rs`, Linux's lock-word protocol: owner TID,
  `FUTEX_WAITERS`, `FUTEX_OWNER_DIED`), so the probe returns 0 and PI mutexes
  really work. The session exports `ALSOFT_DRIVERS=pulse,alsa` and
  `PULSE_SERVER=unix:/run/pulse/native`: openal-soft uses libpulse against the
  system daemon, and if Pulse is not there it falls back to ALSA (which
  `/etc/asound.conf` also routes through Pulse). See
  [README-audio.md](README-audio.md).
- **gzdoom** hung right after printing `GZDoom 4.14.2 - - SDL version / Compiled
  on ...`, deaf even to `^C`. **It was not the session bus**: with
  `DBUS_SESSION_BUS_ADDRESS=unix:path=/sin-bus` it hung the same. They were two
  kernel bugs on the path of musl's `__synccall`, which is what `seteuid()`
  runs: the calling thread blocks all signals, sends `SIGSYNCCALL` to each of
  the other threads and waits for all of them to check in. (1) The mapping dump
  gave the permissions of the mapping's **first** page to all of it, and musl
  puts each thread stack's guard page at the **bottom**, so every thread stack
  looked non-writable and the kernel could not place the signal frame there
  (`nowhere to put the SIGRT34 frame`). (2) A `FUTEX_WAIT` with no deadline
  could not be interrupted by anything, so a thread inside `pthread_cond_wait`
  never checked in. Both are fixed
  ([PR #1601](https://github.com/Pryancito/eclipse/pull/1601)) and gzdoom
  starts. The wrapper's D-Bus muzzle stays for hygiene, but it did not fix
  anything; see [README-dbus.md](README-dbus.md).

## Keyboard shortcuts

| Shortcut | Action |
|---|---|
| `Alt+Space` / `Alt+F2` / `Ctrl+Alt+Del` | Search launcher (`lunarrun`) |
| `Super+Enter` / `Alt+Enter` / `Ctrl+Alt+T` | Open a terminal (`foot`) |
| `Super+E` | File manager (`eclipse-files`) |
| `Super+D` | Show desktop (minimise or restore everything) |
| `Ctrl+F1..F4` | Go to desktop N (the KDE keys) |
| `Alt+Shift+Tab` | Previous window |
| `Super+↓` | Minimise |
| `Super+Space` | Desktop menu |
| `Super+K` | Cycle keyboard layout (`es` / `us`) |
| `Alt+Tab` | Switch window |
| `Alt+F4` | Close window |
| `Super+↑` | Maximise / restore |
| `Super+←` / `Super+→` | Snap to half the screen |
| `Super+1..4` | Go to desktop N |
| `Super+Shift+1..4` | Move window to desktop N |

The layout starts as `es` (console, labwc and Xwayland). It is changed on the fly
with `eclipse-kbd toggle` (or `es`/`us`), the `Super+K` shortcut, the panel's
**ES/US** pill, or `echo us > /proc/kbd` plus `eclipse-kbd us` for the desktop.
It is stored in `/etc/eclipse/keyboard`; at boot `kbd=us` on the cmdline wins.

The UI language is independent of the keyboard. The default is `es`
(`LANG=es_ES.UTF-8`, `LANGUAGE=es:en`). `lang=en` on the cmdline or
`eclipse-locale en` (persisted in `/etc/eclipse/locale`) selects English in
labwc, lunarbar, Firefox/GTK (gettext) and the menu. `LC_ALL` is not exported.

The time zone follows the **country**, not the keyboard: Spain by default
(`TZ=Europe/Madrid`, `/etc/eclipse/timezone`). `country=US` or `eclipse-tz US`
switches to `America/New_York`; `tz=Europe/Paris` sets an arbitrary Olson zone.
`ntpd` (OpenNTPD, or busybox if the applet is there) starts with the system after
DHCP and sets the clock.

## The panel and system stability

The panel is `lunarbar`, a native Wayland client (wl_shm, no GTK, no GL), so it
does not go through the GL/GBM path that can hang the system on this hardware
(see the note in the `/usr/local/bin/labwc` wrapper). It is supervised by
`eclipse-init`: if it dies it is relaunched with exponential backoff and the
console's `respawn:` line says how it ended (`exit N` / `signal N`).

## Diagnosis

- `labwc` writes to `/tmp/labwc.log` (the destination of `labwc.service` and of
  the wrapper).
- Every service that dies shows up on the console (`[eclipse-init] respawn:
  ... exited after ...`), and a missing client is announced by its wrapper in the
  log and on `/dev/console` (`not installed`) before waiting 60 s.
- `lunarbg --dump /tmp/out.raw:1920x1080` and `lunarbg --bench` let you check
  the renderer without a compositor.

If the system hangs when the session starts and you need to get in without a
desktop: switch to another virtual console (`Ctrl+Alt+F2`) and stop the
compositor (`pkill labwc`; init will relaunch it, so to keep it stopped delete
`/etc/eclipse/services/labwc.service` or boot with `desktop=xorg`).

## Customisation

- **Wallpaper**: `lunarbg` is procedural; `LUNARBG_STATIC=1`/`--static`
  disables the animation and `LUNARBG_FPS`/`--fps` changes the cadence (edit the
  `/usr/local/bin/eclipse-lunarbg` wrapper or the scene in
  `tools/lunarbg/src/scene.rs`). The PNG at
  `/usr/share/backgrounds/eclipse/eclipse-night.png` is regenerated outside a
  full build with `cargo test -p xtask dump_wallpaper -- --ignored`.
- **Whole look**: `eclipse-look tecno|eclipse|kde|win11` (see above).
- **Tweaks without rebuilding**: labwc reads `~/.config/labwc/themerc-override`
  **on top of** the theme, so you can change colours, borders or shadows there
  without touching the theme or the build; `xtask` neither creates nor overwrites
  that file. Reload with `labwc --reconfigure`.
- **Third-party themes**: any Openbox 3.6 theme (those from box-look.org,
  Kaunas, Fluent...) works as is: copy its folder to
  `/usr/share/themes/<Name>/openbox-3/` and put that name in `rc.xml`'s
  `<name>`. Bear in mind that `eclipse-look` rewrites that line, so changing the
  look overwrites it.
- **Theme colours**: edit the active look's `themerc`
  (`/usr/share/themes/{Tecno-Dark,Win11-Dark,Breeze-Dark,Eclipse-Dark}/openbox-3/themerc`)
  and run the menu's "Reload labwc" action (or `labwc --reconfigure`).
- **Panel**: `lunarbar` has no configuration file; its palette and layout come
  from `/etc/eclipse/look` (`ECLIPSE_LOOK=` overrides it for a single run) and
  any other change goes in `tools/lunarbar/src/` (`draw.rs` for the look,
  `apps.rs` for the menu); `pkill lunarbar` relaunches it through init with the
  new binary.

Bear in mind that the files under `/root/.config` and `/usr/share` are written
by `xtask` when building the rootfs: persistent changes must be made in
`xtask/src/linux/desktop.rs`.

## Choosing the session: labwc or Xorg

Eclipse ships two desktop sessions and `eclipse-init` (PID 1) starts only one,
in this order (the first one found wins):

1. **Boot argument** `desktop=<labwc|xorg>` on the kernel cmdline
   (`/proc/cmdline`). It is what `make qemu` uses, setting `desktop=labwc` by
   default (`desktop=none` with `VARIANT=minimal`). For the Xorg session
   (framebuffer/`fbdev` on `/dev/fb0`): `make qemu DESKTOP=xorg`.
2. **File** `/etc/eclipse/desktop` (first token): a persistent per-installation
   override you can edit. It is installed with the value `labwc`.
3. Default: **labwc**.

Since real hardware boots with the installed cmdline (no `desktop=`), it falls
back to the `/etc/eclipse/desktop` file and uses **labwc**; `make qemu` does too,
unless given `DESKTOP=`. Each session's services carry a `desktop =` tag in their
`*.service` (`/etc/eclipse/services/`): `seatd`/`labwc` are `desktop = labwc`,
`xorg` is `desktop = xorg`, and untagged services (e.g. `udhcpc`) always start.

`make vbox` boots the **same** live session as `make qemu` (`desktop=labwc`, an
initramfs with Mesa/labwc). The ISO (`make iso` / `./scripts/vbox-eclipse.sh --iso`)
is the installer: cmdline `desktop=none` and an SFS without a desktop, so
`eclipse-init` leaves the console and does not launch the compositor. After
`install-eclipse`, `./scripts/vbox-eclipse.sh --disk-only` boots labwc from the
installed VDI.
